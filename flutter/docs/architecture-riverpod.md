# Architecture & Riverpod conventions

Read this before scaffolding a project, writing providers, or adding a repository.

## Contents

## Layering

Three layers per feature. The dependency arrow points one way only: presentation → application → data. Nothing points back up.

| Layer | Contains | Knows about Firebase? |
|---|---|---|
| **presentation** | widgets, screens, controllers (`Notifier`/`AsyncNotifier`) | No |
| **application** | domain models, use cases (only where logic spans repos) | No |
| **data** | repositories, DTOs, Firebase SDK calls, converters | Yes — exclusively |

The point of the boundary is not tidiness. It is that Firebase types are untestable without emulators, `FirebaseException` codes are stringly-typed, and a `DocumentSnapshot` in a widget makes that widget impossible to render in a test. Repositories convert SDK types into domain models and SDK errors into domain failures at the edge; nothing above the data layer ever imports `package:cloud_firestore` or `package:firebase_auth`.

The SDD may specify a different architecture. If it does, the SDD wins — raise the conflict rather than silently applying these defaults.

## Feature structure

Feature-first, not layer-first. Layer-first (`lib/widgets/`, `lib/models/`) forces a change to one feature to touch four directories and makes deleting a feature a scavenger hunt.

```
lib/
  main.dart
  firebase_options.dart          # generated by flutterfire configure — never hand-edit
  core/
    router/                      # GoRouter config + auth redirects
    theme/
    errors/                      # AppFailure hierarchy
    providers/                   # cross-cutting providers (firebase instances)
  features/
    auth/
      data/auth_repository.dart
      application/app_user.dart
      presentation/sign_in_screen.dart
                   sign_in_controller.dart
    <feature>/
      data/ application/ presentation/
```

## Riverpod rules

**Codegen (`@riverpod` + `riverpod_generator`) unless the project already does otherwise.** It removes the provider-type decision, makes `family` arguments type-safe, and makes refactors compile-checked. Match the existing project if it uses manual providers — mixing both styles is worse than either.

**Provider shape by purpose:**

| Purpose | Use |
|---|---|
| Dependency (repository, SDK instance) | plain `@riverpod` function returning the object |
| Reactive read of a stream | `@riverpod` function returning `Stream<T>` |
| Screen state with actions/mutations | `@riverpod class X extends _$X` — `AsyncNotifier` when the initial state is async |
| Derived value | plain provider composing others with `ref.watch` |

**Hard rules, each preventing a specific bug:**

- `ref.watch` in `build`; `ref.read` in callbacks. `watch` in a callback captures a stale value and rebuilds unpredictably.
- Never mutate state in `build`. Providers must be pure at construction, or dependents rebuild in loops.
- No `BuildContext` inside providers. Providers outlive widgets; a captured context is a crash waiting for a rebuild.
- Controllers hold `AsyncValue<T>` and set `state = const AsyncLoading()` then `state = await AsyncValue.guard(...)` for mutations. `guard` is what stops a thrown exception from becoming an unhandled zone error.
- Render `AsyncValue` with `.when(data:, error:, loading:)` — all three branches. Every Firebase-backed screen has a real, reachable error state; a `!` or a bare spinner is a bug report waiting to happen.
- `autoDispose` is the default under codegen. Use `@Riverpod(keepAlive: true)` deliberately (auth state, config) and be able to say why.
- `ref.invalidate` to refresh; don't hand-roll cache flags.
- Never construct a repository inside a widget. It defeats overriding in tests, which is the whole reason the layer exists.

**Auth gating:** one `@Riverpod(keepAlive: true) Stream<AppUser?> authState(...)` fed by the auth repository, consumed by the router's redirect. Not per-screen checks — those drift out of sync and leak protected screens.

## Error handling

Repositories catch `FirebaseException` and throw domain failures:

```dart
sealed class AppFailure implements Exception {
  const AppFailure(this.message);
  final String message;
}
class AuthFailure extends AppFailure { const AuthFailure(super.message); }
class NetworkFailure extends AppFailure { const NetworkFailure(super.message); }
class PermissionFailure extends AppFailure { const PermissionFailure(super.message); }
```

Map SDK error codes to these once, in the repository. Two reasons: the UI must never branch on `'permission-denied'` string literals, and the code→message mapping is user-facing copy — which means it belongs to the spec, so take the wording from the docs if the docs specify it, and ask if they don't.

`permission-denied` in normal operation usually means the security rules are wrong, not that the user did something wrong. Investigate the rules before writing an error message about it.

## Testing

Test what the spec asserts, at the layer where the logic lives:

- **Repositories** — with `fake_cloud_firestore` / `firebase_auth_mocks`, or hand-written fakes behind the repository interface. Assert conversion and error mapping.
- **Controllers/notifiers** — `ProviderContainer` with `overrides: [xRepositoryProvider.overrideWithValue(FakeX())]`. Always `addTearDown(container.dispose)`. Assert the `AsyncValue` sequence, including the error path.
- **Widgets** — `ProviderScope(overrides: [...])` around the widget. Assert the three `AsyncValue` branches render.
- **Security rules** — the rules are code and belong under test with the emulator suite where the project supports it. Rules are the only thing standing between a client-side app and its whole database; "we'll test them manually" means untested.

Name tests after the requirement ID they cover (`test('FR-03: rejects expired session', ...)`). That's what makes the ledger auditable instead of aspirational.
